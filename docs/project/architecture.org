Geometry, meshing, and solver code that depends on the conical-bearing model
lives under =bearings/conical_journal=.  CGNS and Fluent adapters live at the
package root because they translate file formats rather than bearing physics.

The command-line interface in [[file:../../bearing_cfd/cli.py][=cli.py=]] uses
explicit =argparse= dispatch.  Each command passes control to the corresponding
module's =main()= function.

* Geometry data

[[file:../../bearing_cfd/bearings/conical_journal/geometry/model.py::class GeometryInputs][=GeometryInputs=]]
contains independent user inputs.  [[file:../../bearing_cfd/bearings/conical_journal/geometry/model.py::class ResolvedGeometry][=ResolvedGeometry=]]
contains derived quantities such as eccentricity components, feed bounds,
clearance extrema, and cone slope.  Both records are immutable.

The serialized =params.json= representation is the boundary between CAD and
meshing.  Mesh generators read its =resolved_parameters= rather than repeating
the CAD defaults.

* Coordinate systems and units

| Space | Coordinates | Unit |
|---+---+---|
| CAD | Cartesian =x,y,z=; bearing axis along =+Z= | mm |
| unwrapped master surface | circumferential arc coordinate and axial =z= | mm |
| solver mesh | Cartesian =x,y,z= | m |
| Reynolds--JFO grid | circumferential angle and axial =z= | rad, m |

The mesh generators evaluate the eccentric-cone equations before converting
coordinates to metres.  Reports record the coordinate unit and bounding box so
a missing or repeated =0.001= conversion is detectable.

* Mesh representations

Each mesh generator owns one canonical in-memory array representation.  Gmsh,
VTU, NPZ, CGNS, and Fluent files are derived from those arrays and read back
for comparison.

| Mesh | Canonical representation |
|---+---|
| no-port and surface-inlet Hex8 | points, Hex8 connectivity, external Quad4 groups, and cell fields |
| body-fitted inlet Hex8 | body-fitted points/connectivity plus feed-rim and quality metadata |
| central-feed Prism6 | master Tri3 topology, swept Prism6 cells, external Tri3/Quad4 groups, and internal-mouth census |

Imported entity tags and writer-generated numbering are not stable identifiers.
Round-trip audits compare coordinates, connectivity signatures, physical names,
and group membership independently of numbering.

* Validation and publication

Every stage writes into a sibling staging directory.  It validates the staged
files and replaces the destination only after all mandatory checks pass.
[[file:../../bearing_cfd/artifacts.py::def publish_generation][=publish_generation()=]]
adds =run.json= before the atomic replacement.

Geometry and mesh failures may publish a separate =*.failed= directory that
contains reports but no solver-eligible output.  A rejected STEP batch uses
=*.rejected-step= and never appears in the accepted native-BREP directory.

The stage report contains detailed domain checks; =run.json= records the
generation identity, inputs and units, source revision, producer hashes,
upstream hashes, tool versions, output hashes, and acceptance state.

* Solver separation

The Python and OpenFOAM Reynolds--JFO solvers implement the same physical model
through separate assemblies.  Neither imports the other's discrete operators.
Their comparison therefore detects implementation differences while retaining
independent numerical paths.  Shared assumptions such as rupture pressure,
feed geometry, and axial boundary conditions require separate physical
validation.
