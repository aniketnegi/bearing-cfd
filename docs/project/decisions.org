#+TITLE: Design Rationale
#+UPDATED_AT: [2026-08-02 Sun]
#+STARTUP: content
#+OPTIONS: toc:2 num:nil

* Model the lubricant domain

The CAD and meshes represent the connected lubricant volume, not the bearing
metal.  The construction unites the bore blank with the feed passage and then
subtracts the journal.  Subtracting the journal last trims the passage against
the exact journal surface and avoids a second downstream interpretation of the
void.

The journal and bushing solids are optional visual context.  They are not part
of the fluid cell zone.  See
[[file:../geometry/cad-construction.org][CAD construction]].

* Preserve the bearing's clearance convention

The input clearance is radial at the same axial coordinate, not the shortest
distance between the two conical surfaces.  Geometry construction and
through-gap layering therefore follow bearing-centred radial rays.  Surface-
normal distance is checked separately because it differs by a cone-angle
factor.

Solver-eligible domains cover the full circumference.  A rotating wall does
not satisfy the mirror condition required by a diametral half-domain.  See
[[file:../geometry/clearance-mathematics.org][Clearance mathematics]].

* Keep native BREP and STEP status separate

Native OCCT BREP is the geometry contract for Gmsh.  Its round trip remains at
kernel-level numerical error.  STEP is an exchange output with an independent
strict re-import audit; rejection of STEP does not invalidate a passing BREP.
The project does not loosen the STEP tolerance or feed rejected STEP geometry
to a mesher.

Gmsh preflight disables automatic OCC healing, sewing, and fuzzy Boolean
behaviour.  Silent repair would hide whether the imported topology still
matches the accepted CAD.  See [[file:../geometry/interchange.org][Geometry
interchange]] and [[file:../meshing/brep-preflight.org][BREP preflight]].

* Use a mesh whose topology matches the physical question

The repository keeps four volume-mesh representations because they encode
different domains or inlet boundaries:

| Mesh | Feed representation | Intended use |
|---+---+---|
| no-port Hex8 | none | geometry, periodicity, quality, and convergence reference |
| surface-inlet Hex8 | selected stationary-bore faces | reduced film model with a mesh-aligned pressure patch |
| body-fitted-inlet Hex8 | conforming circular stationary-bore patch | reduced film model with controlled feed area |
| central-feed Prism6 | resolved passage and remote inlet disk | studies that retain passage hydraulics |

The central-feed mesh uses a Gmsh-generated Tri3 master surface and explicit
analytic Prism6 sweeps.  At the feed mouth, film and passage cells reuse the
same nodes and faces.  Each mouth face has two owners and is excluded from the
external boundary groups; exporting it as a wall or cap would disconnect the
fluid path.

The central-feed classifier currently requires
=0 < eccentricity_ratio < 1=.  At zero eccentricity the coaxial journal and
bore cones need a different analytic face classifier, so the current code
rejects that case instead of skipping the BREP check.

See [[file:../meshing/index.org][Mesh families]].

* Treat canonical arrays as the mesh identity

The central-feed mesher publishes coordinates, Prism6 connectivity, external
faces, mouth faces, fields, and tags in =mesh_arrays.npz=.  Exporters construct
MSH, CGNS, and Fluent files from those arrays.  They do not remesh the BREP or
copy a previous format file.

Each exported file is reopened and compared semantically with the canonical
arrays.  This permits harmless tag or storage reordering while still detecting
coordinate, connectivity, group-membership, orientation, or scale changes.
See [[file:../interchange/canonical-source.org][Canonical interchange source]].

CGNS boundary conditions must exist in the CGNS hierarchy.  The exporter uses
Gmsh's CGNS writer, changes surface boundary-condition locations from
=CellCenter= to =FaceCenter= under a byte-preservation check, and then reopens
the result.  The native Fluent ASCII writer is retained because it provides a
direct face-owner representation without relying on the CGNS reader.

* Separate static validation from live solver acceptance

File creation and static re-import cannot establish that Fluent accepts a
mesh.  Static export therefore reports =STATIC_PASS_FLUENT_NOT_RUN=.  A real
Fluent process must import the mesh, run its mesh check, verify zone counts and
scale, and save the native mesh before the status becomes
=FLUENT_IMPORT_PASS=.

OpenFOAM conversion follows the same boundary: =gmshToFoam= and =checkMesh=
prove conversion and mesh acceptance, not boundary-condition correctness or a
converged physical model.  See
[[file:../interchange/fluent-import-audit.org][Fluent import statuses]] and
[[file:../operations/openfoam-conversion.org][OpenFOAM conversion]].

* Publish complete generations

Geometry, mesh, export, and simulation outputs are assembled in staging
directories and moved into place only after their checks complete.  A failure
cannot mix a new report with existing solver files.  =run.json= records the producer,
inputs, upstream hashes, tools, outputs, acceptance state, and replaced
artifact identity.

Optional GUI launch occurs after publication and cannot change acceptance.
See [[file:../operations/outputs-and-reports.org][Outputs and reports]].

* Keep numerical physics outside mesh generation

Boundary names do not specify pressure reference, lubricant properties,
rotation, rupture law, gas or vapour physics, or convergence criteria.  Mesh
generation ends with geometry, topology, quality, and format checks.  Python
and OpenFOAM solvers own their physical inputs and numerical gates separately.

The Python and OpenFOAM Reynolds--JFO implementations remain independent.
Agreement between them detects implementation disagreement but cannot validate
shared equations or assumptions.  The JFO result remains a numerical
sensitivity result until feed geometry, grid convergence, local conservation,
and comparison with independent pressure data are complete.  See
[[file:../studies/conical-journal/reynolds-jfo-validation.org][Reynolds--JFO
verification and validation]].
